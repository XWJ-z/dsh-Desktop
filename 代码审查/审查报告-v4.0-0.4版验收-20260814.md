## 二、新问题 N1：日志时间晚 8 小时 🔴（必须修复）

**现象（老大反馈）：** 日志时间不对，晚 8 小时。

**根因：** `appendLog` 使用 `new Date().toISOString()`（main.js:98）——**toISOString() 返回 UTC 时间**（ISO 8601，Z 结尾），中国时区为 UTC+8，故显示时间比本地时间晚 8 小时。
**连带问题：** `logPath()` 的日志文件名日期（main.js:82）同样用 UTC——本地深夜（如 00:30）运行的日志会被归到**前一天**的文件名。

**修复方案：** 新增本地时间格式化函数，替换两处：
```js
/** 本地时间戳（yyyy-MM-dd HH:mm:ss），解决 UTC 与北京时间差 8 小时 */
function localTimestamp() {
  const d = new Date();
  const p = (n) => String(n).padStart(2, '0');
  return `${d.getFullYear()}-${p(d.getMonth() + 1)}-${p(d.getDate())} ${p(d.getHours())}:${p(d.getMinutes())}:${p(d.getSeconds())}`;
}
/** 本地日期（yyyy-MM-dd），用于日志文件名（避免深夜日志归到前一天） */
function localDate() {
  const d = new Date();
  const p = (n) => String(n).padStart(2, '0');
  return `${d.getFullYear()}-${p(d.getMonth() + 1)}-${p(d.getDate())}`;
}
```
替换：
- main.js:82 `const stamp = new Date().toISOString().slice(0, 10);` → `const stamp = localDate();`
- main.js:98 `[${new Date().toISOString()}]` → `[${localTimestamp()}]`

**验证：** 启动应用，日志时间与系统时间一致（±1秒）；深夜启动日志归到当天文件名。

## 三、新需求：启动界面再优化方案

现状已有：logo、spinner、阶段指示器（①~④）、日志框、错误条。建议按性价比分层：

### 优化1（推荐，P1）：下载进度可视化
- 现状：阶段②只有文字"下载/安装"，无进度感（npm install 可能几分钟）
- 方案：npm 12 支持 `--json` 输出 progress 事件，主进程解析后经 IPC 推送百分比；或轻量方案——阶段②期间轮询 `dshenv` 目录体积（每2秒），显示"已下载 xx MB"
- 效果：用户看到数字在涨，知道在干活

### 优化2（推荐，P1）：版本信息展示
- 页面底部加一行小字：`DSH-Desktop v0.4.0 · DSH 0.1.0-rc.6`
- preload 已有 getVersion()，DSH 版本可经 IPC 新增 `dsh:installed-dsh-version`
- 效果：用户/客服一眼看到版本，报障更高效

### 优化3（可选，P2）：日志区折叠
- 现状：日志框常显 180px 高，普通用户被技术信息淹没
- 方案：默认折叠为一行"查看详细日志 ▾"，点击展开；**出错时自动展开**（收到 error 级日志）
- 效果：界面更清爽，排查时又能看到日志

### 优化4（可选，P2）：视觉细节
- 阶段②时显示不确定进度条（动画），④就绪时阶段显示✓动画
- logo 入场动画（fade-in + 轻微 scale）
- 背景加极淡的网格/渐变纹理

### 优化5（可选，P3）：首次启动提示文案
- subtitle 根据"是否首次"变化：首次→"首次启动需要下载 DSH 运行时（约几十MB），请耐心等待"；二次→"正在启动 dsh web 服务…"
- 判断：`fs.existsSync(dshRuntimeDir())` 或 installedDshBin 是否存在
